# Contributing to exchange_calendars

All of the exchange calendars are maintained by user contributions, and contributions are very welcome.

This document describes:
- the workflow to add a new calendar.
- the workflow to modify an existing calendar.
- how to raise a pull request (PR).
- what's asked of a PR that employs an AI agent.

## Workflow to add a new calendar

Refer to existing calendar and test classes as you work through the workflow.

1. Add the calendar module `exchange_calendars/exchange_calendar_{Exchange MIC}.py`. The module should contain a subclass of the abstract base class `ExchangeCalendar` (in `exchange_calendars/exchange_calendar.py`).
    - Name the subclass `{Exchange MIC}ExchangeCalendar`.
    - Override methods and properties as required, being guided by the `ExchangeCalendar` documentation and in-code comments. All abstract properties must be overridden.
    - Include references or links for holidays and timings (either in the class documentation or as comments).
2. Import the calendar class to `exchange_calendars/calendar_utils.py` and add the class to `_default_calendar_factories`.
3. Add the calendar test module `tests/test_{Exchange MIC}_calendar.py`. The module should contain a subclass of the test base class `ExchangeCalendarTestBase` (in `tests/test_exchange_calendar.py`).
    - Name the subclass `Test{Exchange MIC}Calendar`.
    - Override fixtures as required, being guided by the `ExchangeCalendarTestBase` documentation and in-code comments. The `calendar_cls` and `max_session_hours` fixtures must be overridden.
4. Add a .csv file containing the expected timings to `tests/resources/{Exchange MIC}.csv`. The file can be generated by executing `python etc/make_exchange_calendar_test_csv.py {Exchange MIC}` (see the script's documentation).
5. Add the new exchange to the [Calendars](README.md#calendars) table of the README.
6. Raise a PR (see [Raising a PR](#raising-a-pr)).

## Workflow to modify an existing calendar

1. Modify the calendar class as required.
2. Modify the test resources file (for example `tests/resources/{Exchange MIC}.csv`), either manually or by executing `python etc/make_exchange_calendar_test_csv.py {Exchange MIC}`.
3. Check whether any of the fixtures in `tests/test_{Exchange MIC}_calendar.py` need updating to reflect your changes.
4. Add references for any new or modified holidays to `exchange_calendars/exchange_calendar_{Exchange MIC}.py`.
5. Raise a PR (see [Raising a PR](#raising-a-pr)).

## Raising a PR

How the PR body is written depends on whether the PR employs an AI agent:
- no agent: GitHub fills the PR body with the PR template. Describe the change, then complete the template's checklist that applies to the PR (if any) and delete any checklist that does not apply.
- an agent: the agent writes a body that replaces the PR template. See [Using AI agents](#using-ai-agents).

## Using AI agents

You're welcome to employ an AI agent (for example Claude Code, Codex or Copilot) in your work on a contribution. If a PR employs an agent, the PR must be raised following the repository's [`create-pr`](.agents/skills/create-pr/SKILL.md) skill. That skill has the agent lay out the PR body as the [`pr-body-layout`](.agents/skills/pr-body-layout/SKILL.md) skill defines. This applies whatever part the agent played, even if the agent only advised on the work or only prepared the PR. Agents that read this repository's `AGENTS.md` file are directed to the `create-pr` skill. If your agent doesn't read `AGENTS.md`, point it to the two skills.

The layout opens with a short summary of the PR and a statement of how independently the agent worked. You're then asked to declare which parts of the PR you've reviewed: the title, the summary, the diff across the code base, the diff across the test suite, the commit messages and the agent's detailed account of the PR. The agent leaves each declaration for you to make.

Please be honest in the information that you provide in the PR body. We don't ask for this information in order to reject PRs that employ agents. We ask for it to understand the agent's involvement in the PR and the degree to which you've reviewed the agent's work. That said, if it looks as if we'd be required to review more of the PR than you reviewed, the PR is unlikely to be accepted.
