# PR body layout

In this skill, **the user** is the person you are working with. The user is responsible for the PR and will submit it under their name. In the PR body itself, the user is referred to as **the contributor**.

The layout exists because an agent-written PR body is usually too long for a reader who wants only an overview and the most important aspects of the PR. The summary at the top is the only part that most people will read, hence the summary must stand on its own. The full detail remains available in a fold at the end of the body.

## The layout

In the following template, `{curly braces}` mark placeholders for you to replace (braces included). Angle brackets are literal HTML and stay exactly as written.

```
🤖 {Attribution verb} {Agent} (agent autonomy {level}/5)

### Summary

{Summary}

---
- [ ] I've reviewed/revised the PR title (if unticked, treat it as an agent's unchecked title).
- [ ] I've reviewed/revised the summary above and it covers what a reviewer needs to know (if unticked, treat it as an agent's unchecked summary).

### Agent autonomy

{one sentence, see below}

### Contributor review

I have reviewed the (tick all that apply):

- [ ] full diff across the code base
- [ ] full diff across the test suite
- [ ] commit messages
- [ ] agent's detail below

<details><summary>{Provider} {Model} {Effort}</summary>

{The PR body as you would otherwise have written it, including its usual closing attribution line}

</details>
```

Keep the blank line after the `<summary>` line and the blank line before `</details>`, as GitHub does not render the markdown inside the fold without them.

## Attribution line

The attribution line is the first line of the body. It takes the form that the template gives, in which:
- `{Attribution verb}` and `{level}` are a verb and an autonomy level that the table below pairs.
- `{Agent}` is your name, written as a link to your home page, for example `[Claude Code](https://claude.com/claude-code)`. Omit the link if you do not know the address.

The line carries nothing else. In particular, it carries no session link.

The autonomy level describes how independently you worked. It describes the working arrangement, not the quality of anyone's work. At 5/5 you worked largely on your own, whilst at 1/5 the user did most of the work themselves.

| Level | Verb | Use when |
|---|---|---|
| 5/5 | Generated by | The user supplied the task and little else; you made the design and implementation decisions. |
| 4/5 | Built with | The user steered by adjusting plans or giving corrections; you still made most decisions and were responsible for all or nearly all of the implementation. |
| 3/5 | Crafted with | The user made the key design decisions and drove several rounds of revision; you mostly carried them out. |
| 2/5 | Assisted by | The user directed the implementation itself, not just the design: they specified the structure, names and logic in enough detail that you were largely transcribing their intent, or they wrote or supplied a substantial part of the change. |
| 1/5 | Advised by | The user wrote or supplied most of the change themselves; you advised, reviewed, wrote minor parts, or only prepared the PR. |

The verb and the level always go together, as the table pairs them. For example:

```
🤖 Crafted with [Claude Code](https://claude.com/claude-code) (agent autonomy 3/5)
```

Judge the level only from what the session saw:
- the work done in the session, by you or by the user.
- what the user supplied to the session, for example a file, text given in the conversation or the commits of a branch. Take what the user supplied to be the user's contribution, as the level describes the working arrangement and not who first wrote a text. As an exception, take a supplied commit that names an agent (as its author or in a `Co-Authored-By` trailer) to be principally that agent's work.
- the direction that the user gave in the session. Direction is what the user decided, changed or specified. An approval of what you proposed, given without change, is not direction.

Do not credit the user with work or direction that the session did not see. If the evidence leaves you between two levels, use the higher level.

### A footer added by a tool

A tool that creates or updates the PR may append a footer that resembles the attribution line, for example "Generated by Claude Code". Leave any such footer in place, and do not raise it with the user. A session link in such a footer does not break the rule that the attribution line carries no session link.

## 1. Summary

The summary is written for a reader who has not seen the session and will read nothing else. It states what the PR changes, why, and anything that a reviewer must know before merging (for example a risk, a migration, or a decision that the reviewer is being asked to accept). Where the summary makes more than one point, write it as a short lead-in that ends with a colon, followed by a bullet for each point. Aim for fewer than 100 words. Go past 125 words only if a reviewer would otherwise miss something that they must know, and never go past 200 words. Include an image only if one already exists at a URL and the image explains the change faster than words would.

Follow the summary with the separator, the title checkbox and the summary checkbox, exactly as shown. Leave both checkboxes unticked. The separator (`---`) stops the checkboxes from being read as further items of a bulleted summary. Keep the blank line before the separator (as a `---` directly under a line of text turns that line into a heading).

## 2. Agent autonomy

Write one sentence, in your own voice, that gives the evidence behind the autonomy level that you chose. For example: "The contributor set the approach and requested two rounds of changes to the caching design; implementation and tests were written by the agent." State what you observed, not what you assume. Where the level rests on what the user supplied, say "supplied" rather than "wrote", as the session did not see the supplied work being written.

## 3. Contributor review

Include the lead-in and the checkboxes exactly as shown, unticked. The checkboxes are the user's declarations, hence never tick a checkbox yourself and never remove one. Do not tick a checkbox even if the user tells you in conversation that they have reviewed what the checkbox declares. These rules apply to every checkbox in the body, including the title and summary checkboxes.

## 4. Detail

Inside the `<details>` block, write the PR body that you would otherwise have written. Follow whatever other skills, templates and conventions apply to it, and end it with your usual closing attribution line, unchanged.

The `<summary>` label names the model that wrote the detail. It gives the provider or product family, the model name and the effort level, for example `Claude Opus 5.5 Medium`. State each part to the best of your knowledge - you are not required to be certain of it. If you cannot include:
- the model name, write the placeholder `{Name Model here}` in its place for the contributor to complete, for example `Claude {Name Model here}`.
- the effort level, leave it out rather than guess.

## Updating an existing PR body

If the body already follows this layout:

- Keep the user's edits to the title and to the summary. Change the title or the summary only if later commits have made it untrue. If you change the title, untick the title checkbox. If you change the summary, untick the summary checkbox. In either case, advise the user.
- Keep each ticked box, unless commits made since the box was ticked make its declaration untrue (for example, new changes to the code base after the user ticked "full diff across the code base"). In that case untick the box and advise the user.
- Start from the autonomy level, verb and autonomy sentence that the body already holds, regardless of who set them, as they record the working arrangement of the sessions that you did not see. Move the level only for work done in this session, and only as far as that work's share of the whole change warrants. Change the verb to match the level. Revise the autonomy sentence such that it covers the whole history of the PR.
- If you rewrite the detail, update the `<summary>` label, unless the label already names your model.

## How this combines with other instructions

This skill does not replace other PR-writing skills, repo PR templates or project conventions. Use them to write the detail (section 4 above) - the whole of the body that you would otherwise have produced goes there. This skill governs the overall structure and everything outside the fold. Where anything conflicts with this skill, this skill wins.

## Before submitting

Advise the user that the PR title, the 'Summary' section and the 'Contributor review' section require their attention. If you wrote the `{Name Model here}` placeholder in the `<summary>` label, also advise the user that the placeholder is for them to complete.
